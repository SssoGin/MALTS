# Selected v2 Task execution

Load this only for an actual Task operation or execution/verification repair. Phase, Artifact and migration/recovery reviews use their own focused reference and do not need this file.

## Advance the requested work

Resolve the next useful action from the current goal, acceptance criteria, dependencies, and pending operations. Reuse unchanged, applicable evidence. Update a Task revision when its contract changes; rebind dependencies or Phase versions explicitly when required. A transport session or RPC ID is not a Task, Run, or authorization identity.

Through MCP, send `{action, arguments}` to `malts_request`. Project, actor, and authority fields marked Host-bound are supplied by configuration; do not replace them. Existing Grants must match the current Task revision and actual resource/effect. If one is missing, route the concrete requirement to the trusted controller using the existing authorization where applicable. Ask the user only for a genuinely missing scope decision. The client tool surface intentionally cannot mint Grants or promote its own permission.

The decoded `malts_request` success body is `{"decision":"REQUEST_PROCESSED","action":"<requested-action>","result":{...}}`. Action fields belong to `result`: after preparation use **`response.result.request_hash`**, not `response.request_hash`, as `expected_request_hash`; after a read use `response.result.text` and `response.result.sha256`. Check `decision` first. An error has top-level `decision=ERROR`, `error_code` and `error_type`, and no successful action result. `malts_actions.request_response_contract` advertises these paths. The MCP transport may carry the same decoded body in `structuredContent` or its JSON text block; neither changes the body's field paths. A client helper that explicitly returns only `body.result` has already unwrapped the body; do not confuse that helper with the raw MCP response.

Preparing payload-bearing operations also needs Host-approved protected input capture. Check the advertised capture policy; never supply your own capture authority to bypass a disabled policy. Minimal read-file metadata does not require storing file contents. Protected capture permission is separate from permission to perform an effect.

An `ACCESS_DENIED` response may provide a value-free `reason_code`: `GRANT_NOT_APPLICABLE` covers a missing Grant or another principal's Grant; `GRANT_SCOPE_MISMATCH` covers a resource/effect mismatch; `DISPATCH_NOT_ADMITTED` means this Worker no longer meets current admission. Use current context and the controller's existing authority to diagnose that specific boundary. Report the code without inventing replacement IDs, reviving an exited Worker or treating a read-only context as permission. A generic denial has no proven cause; do not relabel it.

For a write-enabled endpoint pinned to a Task, `malts_context.execution_inputs` returns a bounded list of this actor's existing Grant IDs and resource/effect pairs. Copy the exact ID for the intended resource; never derive an ID from its path. Revocation/expiry metadata and truncation are explicit; this list does not evaluate authorization or replace preparation checks. The same snapshot supplies complete `preimage_policy_templates` when Host capture is enabled. Select the current criterion and pass the full descriptor to update-file; the three summary fields in `evidence_capture_contract` are not a complete descriptor. Templates classify the preimage as protected/unknown, permit verification/recovery/derivation only, preserve recovery references, and do not prove sanitization or authorize Growth. A missing/truncated entry requires a controller handoff, not guessed fields or a new Grant.

Use the effect adapter the current action catalog actually provides. Managed `operation.create-file` and `operation.read-file` perform their own intent, lease checks, and observation; do not pre-commit their intent or claim their outcome separately. Creation is exclusive, not an overwrite operation. Reading a resource can write necessary control records even though it changes no resource bytes. Other effects need their declared qualified adapter or controller path; do not invent a replacement command or use a broader path to evade a client restriction.

Use the exact IDs supplied by this pinned Task's current `malts_context.execution_inputs` or by the trusted controller. Preparing a read requires `parameters={"tool":"read-file","path":"<granted-relative-resource>"}`. Pass `prepare_response.result.request_hash` to `operation.read-file` as `expected_request_hash`; `max_bytes` and `max_characters` are optional execution arguments, not preparation parameters. Empty parameters may prepare a generic operation but cannot execute this file adapter. The action catalog describes each file adapter's nested preparation fields. A `HOST_BOUND_FIELD_MISMATCH` reason identifies only the field to omit, never its configured value; do not guess or override it. `FILE_READ_PARAMETERS_INVALID` identifies the closed read contract; preserve an existing prepared operation instead of replaying it with different parameters.

For an existing ordinary file, the Windows `operation.update-file` profile requires its current byte SHA-256, new UTF-8 content and explicit preimage capture policy in the prepared request. It preserves old bytes before writing and checks the opened file exclusively. A conflict or uncertain outcome is not permission to retry under another ID. The controller can reconcile an update against its saved old/new versions without rewriting; divergent content needs review.

The controller's `update-repair-plan` can bind divergent bytes to a selected old or requested version. An approved repair needs a separate bounded Grant and runs as a new operation; the old failure and divergent preimage remain available. Restoring old bytes does not finish the user's original goal.

## Verify the result, then determine completion

If `malts_actions` reports a Task/dispatch binding, stay within that assigned Task and Run. Use the reported scope; do not switch to another Task, create a replacement Run, or treat a denied stale dispatch as permission to reconnect through a broader endpoint. The controller owns successor dispatch and contract revision. A dispatched Worker produces the assigned artifacts and applicable evidence, then returns their identities and unresolved issues. Final verification/acceptance, rework decisions and cancellation of the Task belong to the controller after the Worker Host settles; those actions are not exposed on its endpoint. Do not keep running merely to attempt acceptance of your own active dispatch.

Use `verification.begin` once registered operations have settled and managed dispatches are resolved. `VERIFYING` blocks new operations, Run creation and Host launches while permitting evidence checks. If the result needs repair, `verification.rework` returns to RUNNING and invalidates the previous evidence basis; it grants no new permissions. Pause/resume preserves verification mode. Small Tasks may use `task.accept` directly: it enters the same verification gate atomically, and still rejects unsettled managed Hosts or effects.

Match the required verification method and evidence level. A client-declared review is not an independent test or a higher-level verifier. Record actual checks through the available evidence interface; do not manufacture a PASS, a verifier identity, or a cost improvement.

MCP `evidence.record` captures only the observed operation's granted file and requires Host-enabled protected capture. Its descriptor must use `content_class=protected-artifact`, `sensitivity=unknown`, and only `verification`/`recovery`/`derivation` purposes within the approved capture scope. A client label does not prove redaction. Growth needs a separately reviewed derivative from the trusted controller, not a relabeling of this raw capture. Encryption protects stored content; it neither proves a PASS nor grants reuse permission.

The controller-only `evidence.derive` binds an independently reviewed body to exact source identities and an observed review Task. Sources must already permit `derivation`; recovery access alone does not permit it. This is not an automatic sanitizer and is unavailable to the MCP worker. Withdrawal, expiry or loss of any transitive source stops derivative reuse, including prepared Growth trials. Preserve retained evidence; a stopped propagation path is not authorization to delete it.

For an explicit `managed-file-integrity` criterion accepting level C, `verification.managed-files` runs the file checks and generates bounded evidence. Supply its Task/operation/criterion identity and capture descriptor; its result, method and level are fixed by the verifier. Keep separate business checks where the user's acceptance requires them.

Use `task.accept` only when the Task's required work and current checks are complete. Managed file-result checks compare current bytes, but do not prove unrelated Editor/network outcomes. A historical acceptance replay or stored `COMPLETED` flag is not fresh verification. Use `malts_verify_task` when the connected MCP server advertises it, or the controller CLI `task-verify --state-dir <state> --task-id <id>`, for a read-only current-proof check; NO_LONGER_PROVEN preserves history and requires investigation or authorized rework. A completed Task also does not finish a larger user objective with remaining required work.

## Resume without replaying uncertain effects

After interruption, inspect the same business Task and Operation IDs. `NOT_REEXECUTED`, `UNKNOWN`, a cancelled RPC, and a stopped transport do not prove that an effect was rolled back. Do not mint a new operation merely to repeat an unresolved effect. Reconcile through the trusted controller/adapter and preserve actual outputs and uncertainty.

`RECOVERY_REQUIRED` identifies a Task with registered UNKNOWN effects. Reconcile the original operation rather than revising the Task or preparing another effect. Unrelated Tasks can proceed under their own contracts. `effect_recovery` remains visible for a cancelled goal; recording a late known result never reopens that goal. Clearing UNKNOWN restores the appropriate control state, not a Grant or proof that the Host stopped.

Restoration does not replenish consumed operation or Host launch budgets. Retain recorded consumption and reconcile post-backup usage; missing usage remains unknown, not zero. A restored Host dispatch budget is revoked with unknown consumption until the controller reconciles it and obtains the corresponding current authorization. Use the current budget contract before a successor launch; a new Run or checkpoint is not a fresh allowance.

When the state root or epoch changes, use the verified new binding. Do not clear legacy seals or revive a superseded store. For ordinary paused work, resume the exact Run/checkpoint only when its current Task/Phase contract and dependencies permit it; otherwise replan the affected work.

`PAUSE_REQUESTED` means registered operations remain unsettled or a registered launched Host still lacks a quiesced observation. Inspect both `pending_operations` and `pending_hosts`; an empty operation list alone is not settlement. Stop new operations and continue the existing effect/Host observation or authorized cancellation path. A cancellation acknowledgement alone is not proof of process exit. Settlement may confirm `PAUSED`, but that control state does not prove that all native or external writers have stopped; migration and takeover require their own Host evidence.

The controller may explicitly withdraw a pending pause with `run.resume` only when the exact Task is WAITING, its checkpoint and contract match, effects/dependencies are resolved, and its existing managed Host is still admitted as RUNNING with a current epoch and valid known budget. `pause_request_withdrawn=true` continues that existing run; it neither launches a replacement process nor proves current liveness. Do not use resume to revive an exited, cancelled, quiesced or revoked Host. Reconcile it and use the authorized successor path when further work is needed.
