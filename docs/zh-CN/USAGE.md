# 在项目中使用 MALTS

项目从可检查目标开始，经计划、执行、验证和交付完成。MALTS 工作流保留中断、协作和后续复盘所需事实。当前版本：**2.0.3**，控制端协议见[操作说明](V2_PREVIEW_USAGE.md)。

## 进入已有工作区

新项目可用 `malts-project-init` 建立适用入口、目标和基本记录；新长期项目使用 `malts-long-project-workspace-init` 建立首个可执行阶段。当前实现的完整长期设置要求 `phase_ready=true`，不是只执行 `init` 或创建空骨架。

已有项目先核适用指令、实际安装入口、工作区绑定和当前任务，不重复初始化。读取当前目标、阶段计划、任务依赖、已验证结果与未解决效果；按需要定位相关历史，避免把整个历史扫描作为每轮前提。

技术上，阶段和任务通过 `phase.bind-task` 绑定准确版本。用户主要需要知道当前目标、正在做的部分和完成条件；详细参数由已安装工作流及控制端处理。

已采用工作区可由控制端先用已验证运行时的 `malts_v2.py workspace --workspace <workspace>` 核绑定，再读 governance-context/task-queue 及准确 context。只读相关当前事实，查询不授权执行。采用前工作区保持原经验证合同；旧 long_workspace 命令不是 v2 写入路径。

从当前任务及剩余条件接续，比较所选计划/依赖与真实输出身份，重试相关工作前核 UNKNOWN。不能仅因更换会话就重新初始化。

只读问题读取相关上下文和文件，不定义新 Phase 或创建受管执行记录。已批准的新工作应判断是否改变当前边界，经服务修订或建立相应阶段/任务。历史计划阶段不能因名称相近自动选用。

Binding 缺失或不一致时保留工作区，核其采用/恢复来源，不能删除绑定或覆盖初始化来获得通过。下一步取决于实际故障，而不是假设项目为空。

## 启动项目

目标清楚、范围小且能立即验证的工作，沿用项目规则即可。跨多轮而需要保留决定时，建立基本项目记录；跨阶段、窗口或执行者时，使用长期工作区。需要分离调查、实施或验证并已授权委派时，使用多 Agent 调度。任务规模、恢复价值和实际资源决定方法。

示例：“使用 MALTS 管理这次代码迁移，先检查现状，明确兼容性和验收，分阶段实施；本次允许项目内修改和验证，不提交或发布。”

说明交付对象、允许修改范围、应保留内容及结束条件。Agent先核可发现事实；有重要不确定取舍时使用 `malts-grill-me-preflight`。澄清结果区分已确认事实、建议与待决定事项，分析本身不修改项目。

例如，把“改好这个模块”明确为“在保持现有接口行为的前提下修复故障，覆盖复现场景和关键正常行为，交付修改及验证结果”。具体目标由用户与项目决定，示例不增加本次权限。

每个阶段保存目标、边界、交付物和验收；任务说明要完成的结果、输入、依赖及检查方式。阶段结束后核完成条件和实际剩余工作，新目标另行建立阶段，不自动激活历史计划。

任务分解应使结果可以独立检查，避免只有动作清单而没有交付标准。强依赖工作按顺序执行；可以分离的工作再评估并行价值。重要需求变化重新核受影响计划和版本，无关工作继续。

实际请求可同时说明结果和排除项：

> 使用 MALTS 迁移这个模块。保留公共接口和用户数据，明确兼容检查，完成已批准修改并交付依据。只在本项目工作；部署和公开发布不在本次范围。

Agent 先核现有行为和项目指令，计划区分兼容定义、实施和整合检查，说明每段工作产出，不将每次读文件变成里程碑。

| 工作 | 产出 | 验收问题 |
|---|---|---|
| 确定当前行为 | 审阅接口/输入基线 | 需要保留的兼容性是否明确？ |
| 实施修改 | 实际更新模块 | 是否满足限定行为？ |
| 核集成 | 结果输入/输出上的实际检查 | 必需交互是否仍正确？ |
| 交付 | 结果、用法与剩余限制 | 整体请求是否具备所需依据？ |

这是分解示例，不是每个项目的固定队列。选择长期设置时才建立首个活动阶段，小工作可直接完成。

## 选择合适的工作流

| 工作流 | 用途 |
|---|---|
| malts-grill-me-preflight | 实质未明确目标、约束或验收 |
| malts-project-init | 明确轻量项目设置 |
| malts-long-project-workspace-init | 首次可执行长项目或实际阶段/结构变化 |
| malts-v2-task-workflow | 当前任务、阶段、成果或恢复专题 |
| malts-session-handoff | 跨执行者/窗口的实际接续 |
| malts-single-agent-lightweight-growth | 相关信号之后的不写文件判断 |
| malts-project-retrospective-growth | 已请求/授权的深入复盘 |
| malts-multi-agent-long-task-scheduling | 已授权分工 |

按当前目标选方法，不把全部工作流当作强制链。

## MALTS 何时要求隔离 Preview

安装、迁移、权限、并发或恢复变化可能需要隔离预览。普通内容编辑检查受影响差异/链接并复用未变化行为证据。见[生命周期](LIFECYCLE.md)；预览不是业务验收或生产修改权限。

## 验证项目控制

Agent在当前范围内完成必要修改和适用检查，保留有价值的决定、结果和检查点；不用每次成功都生成报告或刷新时间戳。常规细节自行选择，授权覆盖的必要步骤持续执行。

实际结果优先于自评和状态标签。代码检查行为，文档检查内容和引用，安装检查实际入口和载荷。完整任务的验收不能由其中一个局部检查替代。输入未变且仍适用的证据可以复用；变化或实际风险影响哪些检查，就重核哪些。

当前实现将独立业务要求与文件完整性检查分开。处于验证中而需要修改时，控制端使用 `verification.rework`；交付后 `task-verify` 可以复核当前证明，`CURRENT_EVIDENCE_VALID` 只支持该任务声明的范围。

把实际成果与最初目标逐项核对，区分实现、适用验证、未验证和未完成。阶段或任务接受后保存必要恢复资料，交付用户真正需要的结果。新功能或重大取舍不自动加入本次收尾。

最终说明应足以让用户判断交付：做了什么、怎样使用、怎样验证、还有哪些限制。尚有必要工作时继续；完成当前目标后及时结束，不用报告数量或测试次数代替质量。

检查应说明声明、输入和预期观察。代码覆盖相关正常行为与已知故障，文档核读者需要的完整解释、来源、示例和链接。重复哈希检查不能证明语义正确。

检查失败时保留观察，诊断受影响原因并返工实际结果。处于 VERIFYING 时先 verification.rework 再执行；验收后 task-verify 核当前证明，可保留历史验收并说明变化输入已不能证明。

交付区分已实现、已验证、不可用、失败和明确延期项。证据只支持较窄结果时如实说明，不能将原目标静默降为该子集。新增要求和重大取舍另作范围决定。

## 不改变状态的诊断

正常使用通过工作流获取当前方法；维护者可使用 `workspace`、`governance-context`、`task-queue`、`context` 和 `task-verify`查询事实。只读查询不会初始化或授执行权限，`request`默认预览也不证明执行就绪。

| 观察到的结果 | 下一步 |
|---|---|
| `NOT_APPLIED` | 仅返回预览；核范围与真实就绪后再执行 |
| `NO_LONGER_PROVEN` | 核变化输入和受影响证据，保留历史结果 |
| `UNKNOWN` / `RECOVERY_REQUIRED` | 对账原操作，保留现场 |
| `STALE_PROCESS` | 正常重载宿主后重新核入口 |
| 权限或资源不匹配 | 控制端核现有授权、准确目标与相关写者 |

详细协议见[操作参考](V2_PREVIEW_USAGE.md)，整体功能见[系统说明](SYSTEM_OVERVIEW.md)。

## 治理 Phase 与 Artifact Lifecycle

每个阶段保存目标、边界、交付物和验收；任务说明要完成的结果、输入、依赖及检查方式。阶段结束后核完成条件和实际剩余工作，新目标另行建立阶段，不自动激活历史计划。

任务分解应使结果可以独立检查，避免只有动作清单而没有交付标准。强依赖工作按顺序执行；可以分离的工作再评估并行价值。重要需求变化重新核受影响计划和版本，无关工作继续。

成果记录所属阶段、版本、来源与相关成果。共享前核当前内容和适用条件，旧成果失效时保持历史解释；清理前另核引用与恢复价值。

用户需要持久报告时，报告包括交付内容、验证依据、剩余事项和限制。换窗口或执行者时用 `malts-session-handoff` 保全独有手工内容，生成准确的按需派生视图，说明当前状态和下一步。交接不把历史建议转为授权，也不覆盖较新的项目事实。

Phase 边界说明本阶段交付及不属于此处的工作。验收或实质范围改变时修订，并将受影响任务版本绑定审阅计划。暂停是控制转换，本身不证明原生写者已停止。

登记成果时使用真实所属、内容/版本和依赖；提升 Shared 需审阅复用范围与当前资格。采用实际公开服务，如 artifact.register、artifact.promote、artifact.reconcile，不能从 SUPERSEDED 等状态猜动作名。

退役或清理前核是否仍为输入、传递依赖或必要恢复前像。文件可能已不供下一任务使用，却仍需结清早期中断效果。路径移除/迁移与元数据对账有不同责任。

## 默认安全行为

默认单 Agent、必要范围、准确目标和有意义验证，复用同范围已批准动作。选 Skill 不产生委派、费用、后台、发布或破坏性效果权限。保留个人内容、恢复来源和未知效果。

## Plan Recheck 与 Codex Peer Task

计划/目标实质变化时更新受影响当前阶段/任务版本和绑定。输入未变化不例行重写计划。原生 Peer Task 是已授权调度合同内的宿主执行路径，须有实际身份、输出与控制端验收，不产生额外权限。

## 暂停与接续

继续之前核准确任务、进度和结果；确定上次操作是否完成、是否留下不确定效果，相关进程是否实际停止。未知效果（`UNKNOWN`）表示尚不能确定发生了什么，不等于失败或未执行；沿原操作身份核实，不盲目重试。

暂停请求、暂停状态与实际停止分别判断。恢复使用现有检查点、当前计划和剩余预算；新窗口或恢复不增加原额度。必要备份和后续产生的工作保留。详细步骤见[生命周期](LIFECYCLE.md)与[状态合同](V2_STATE_CONTRACT.md)。

保留当前检查点，同时核受管未决效果和真实宿主状态。操作结清前暂停请求可能持续待定。进程停止不一定有业务结果，业务效果发生也可能没有回执，应分别评估。

合同允许时恢复原合格 Run；需要后继执行时，使用经审阅当前任务/宿主路径，保留原消耗和未知效果。不能只为消除待定状态创建替代 Run。

文件更新提交意图后中断，应经合格对账路径比较原请求/前像与实际字节；外部编辑器/Provider 缺合格观察时，保留未知并在重复前取得相应证据。见[状态合同](V2_STATE_CONTRACT.md)。

## 有价值时分工

调用 `malts-multi-agent-long-task-scheduling`，先审阅能否分离工作、共享资源、实际工具能力和成本。每项委派明确目标、输入、修改范围、预算、返回格式与验收责任；没有对应授权时先准备可审阅分工，其他已授权工作继续。

主 Agent可以委派调查、规划、实施或独立验证，最终整合责任仍保留。Worker返回产物、验证和不确定项；控制端确认执行者结清后核内容、依赖和集成。某个 Worker成功、多个文件存在或多个模型意见一致，都不自动完成项目。

示例分工可以是两个独立模块分别实施，再由另一职责检查集成；共享同一文件或有顺序依赖时，采用串行或明确协调，不强行并行。后台和无人值守另需对应范围。

## 复盘与积累经验

普通任务后有纠正、验证反转、恢复或可复用方法时，可使用 `malts-single-agent-lightweight-growth` 判断是否值得进一步记录；没有信号时保持无输出。重要阶段、反复失败或明确复盘请求使用 `malts-project-retrospective-growth`。

经验记录来源事件、适用问题、建议做法、检查方式和不适用条件。项目内保存与试用使用已有授权；修改长期全局规则或 Skill另外核范围。当前 `growth.propose`、trial、outcome、validate和retire管理候选到后续判断；中性、有害和未知结果保留，退役内容不靠迟到好评复活。

例如，一种检查帮助找到故障，可以先用于适合的后续任务并记录结果；不能仅凭这次成功就要求所有项目永远执行同一流程。

## 工作区管理数据与迁移

普通新工作区通过 `workspace-init` 默认将任务库、受管证据和恢复资料置于所属 `.malts` 目录，显式外置布局继续受支持。安装更新不搬动已有项目。健康已采用库可经只读计划、备份恢复、当前效果审查和正式前向切换重定位；新 epoch 不恢复旧授权或验收，也不自动激活 Phase。旧库、外部历史引用和来源封存按实际依赖保留。操作与限制见[工作区管理与状态库重定位](MANAGEMENT_AND_RELOCATION.md)。
