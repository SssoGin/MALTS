# MALTS 系统概览

MALTS 在 AI Agent 多轮执行中保留项目目标、当前进度、实际结果和恢复信息，通过共用项目/任务合同连接交付、可选协作与有依据的经验使用。当前版本：**2.0.2**。

## 1. 系统目的

MALTS（Multi-Agent Long-Task Scheduling and Growth System，多 Agent 长任务调度与成长系统）是一套用于 AI Agent 项目工作的运行框架。它将任务交付、长期调度、恢复、验证和经验积累连接起来，使工作在多个执行轮次之间保持目标和结果的连续性。

这里的“长期”指工作超出一次提示、一个上下文窗口或一次不中断执行。代码迁移、持续排查、跨模块改动、研究与文档交付都可能有这种需要。MALTS 的核心价值是组织这些工作所需的记录和检查，而不是增加 Agent 数量或为每次对话制造文件。

## 2. 解决的问题

长期项目的困难包括目标被重新解释、进度无法恢复、局部结果被过早宣布完成、共享修改冲突，以及经验没有依据或失去适用性。

MALTS 据此设定五个目标：保留用户意图和完成条件；使当前进度与历史资料可区分；使执行结果可以核查和恢复；明确分工与最终责任；让经验通过后续事实判断价值。项目中的原始数据、现有工具和用户决定始终是这些工作的输入与边界。

长期项目可能在每项局部动作看似合理时失败：摘要遗漏要求，后继重复已执行操作，协作者优化自身任务却破坏整合约束，或有利经验被用于已不具原条件的工作。

MALTS 通过保留原始/当前目标、绑定计划和依赖版本、按稳定身份观察效果、按条件验证产物，以及保留经验适用性处理这些问题。机制使结果更可检查、工作更可接续，其存在本身不证明项目成功率的统计改善。

用户因此同时审阅产物和完成声明：输出是否满足目标，检查是否覆盖声明，剩余限制是否明确。没有真实依据时，大量报告不能回答这些问题。

## 3. 核心运行模型

**交付过程：目标—计划—执行—验证—交付。** 先明确输出和完成条件，再安排任务，检查实际结果，准确说明已完成与剩余工作。

**调度与连续性过程：当前进度—有界工作—检查点—恢复或交接—下一步。** 一轮工作有明确范围和停止条件，后续执行者依据保留下来的事实继续；可以按需要分工，但整体结果仍由主 Agent 负责。

**成长过程：实际观察—原因分析—经验候选—后续试用—保留、修订或停用。** 经验与产生它的事实关联，只有符合当前工作的候选才进入试用，不以一次成功或主观评分直接提升为长期规则。

这三个过程共享项目目标与验证结果。例如，验证发现错误时，交付过程要求修复，连续性过程保留准确进度，成长过程判断这次错误是否说明一种可复用的问题。

## 4. 必需核心能力

### 可恢复项目控制

保存原始目标、当前理解、允许范围、排除项和验收条件。目标或重要事实改变时，重新核对受影响的计划与任务；普通细节由 Agent 自行判断，已授权同范围工作不重复询问。

### 可执行长项目初始化

项目定义整体目标，阶段划分一段有明确交付的工作，任务描述具体可执行、可验证的结果。它们之间的版本和依赖帮助判断旧决定、旧任务结果是否还适用于当前计划。长期工作区必须有可执行的首个阶段，不能只建空目录就宣称设置完成。

### 状态一致性与恢复

执行前核相关输入、现有授权和实际工具条件；执行后保留结果与必要检查点。中断、取消与失败分别处理，先核操作是否发生，再决定下一步。当前实现区分准备、执行意图和观察结果；未知效果保留原操作身份直到对账。

### 验证检查清单

每项工作依据明确的完成条件验收。代码使用相关行为检查，文档核事实、结构与引用，安装核实际入口与内容身份。任务要求、依赖或输出变化可能使旧证明失效；局部测试、进程退出或历史“完成”标签不能代替实际目标的验收。

### 成果管理与复用

成果保留所属阶段、内容版本、来源和关系。需要跨任务共享时，核当前内容与资格；已替代或退役的成果保持历史解释，不自动重新启用。成果的可复用性与是否可以删除是不同问题，必要恢复资料有自己的保留用途。

### 阶段与最终报告

按需说明当前结果和剩余工作，阶段/任务状态不代替用户可读报告。

### 交接与接续

报告说明结果和依据，交接说明当前状态、未解决项、恢复条件和下一步，均按实际需要生成。交接先保全用户独有内容，再核当前事实和目标文件，避免过期视图覆盖新记录。

### 复盘与成长

轻量成长识别实际信号，无信号时不生成空报告。阶段交付、反复失败或明确要求可以进入深入复盘。经验候选声明来源、适用条件、做法、验证和停止使用条件；后续结果包含有益、中性、有害或无法判断，不只保留成功。项目经验与全局 Skill/规则修改分别管理。

### 技能、模板与检查清单

标准 Skill 组织工作流，模板辅助起草目标、任务合同、报告和交接，清单核交付与记忆候选。它们支持项目，不另建状态或权限。

这些能力在一次交付中协同。例如模块迁移中，Project 记录保留接口与不部署边界，Phase 定义有限迁移阶段，任务连接分析、实施和检查，操作记录真实修改，证据支持验收，交接标识剩余兼容工作，复盘可提出后续方法试用。

用户无须手工建立每种记录，所选工作流/控制端提供实际服务操作并解释有用结果。记录由恢复、执行或验证合同需要决定，而不是每轮都必须产出文档。

项目验收范围大于单任务。源码实现、本地验证、安装入口和原生宿主行为是不同证据层，控制端应说明结果证明了哪一层，以及整体目标还欠哪些工作。

## 5. 可选能力

单 Agent 是默认路径，适合目标清楚、修改集中或任务之间依赖较强的工作。多 Agent 适用于独立探索、分离模块、交叉验证或确有并行价值的工作。

协作前明确职责、输入、允许修改范围、资源、预算、交付格式和检查点。主 Agent 负责选择分工、处理共享资源、汇总结果、验证集成和最终接受。更多执行者会增加沟通与整合成本，因此分工须服务于目标，不能只因工作复杂就自动启动。

MALTS 管理已接入接口的资源和执行者；外部编辑器、后台进程和实际宿主能力仍须核实。取消请求、暂停状态与进程实际停止分别检查，不能由其中一项推断其他项。

Git、外部记忆、翻译报告和无人值守依实际需要及相应授权选择，并非每个项目的依赖。

## 7. 典型使用场景

跨模块代码修改、具有兼容检查的工程迁移、跨窗口调查、有限文档/调研交付、明确独立审阅、中断后的接续。每种场景保留实际结果和停止条件，不以任务或 Agent 数量为目标。

| 场景 | 重要的持久信息 | 合适结束条件 |
|---|---|---|
| 接口迁移 | 兼容约束、前置/输出版本、检查 | 约定接口行为已验证 |
| 调查 | 复现输入、观察、被排除假设、下一实验 | 有依据原因/结果，或明确未解问题 |
| 文档交付 | 读者、事实来源、章节要求、审阅限制 | 所需解释与引用已核 |
| 中断执行 | 原操作、当前字节/结果、检查点、Host/预算 | 依赖接续前结清不确定效果 |
| 独立审阅 | 准确产物、审阅条件、整合责任 | 实际问题已解决或明确保留 |

一轮内有界且可恢复的目标可使用轻量项目方式；阶段和依赖需持久权威时采用长期工作区。任务规模不同，不必使用相同形式程序。

## 8. 非目标和边界

已有领域、权限、事务、受管文件、恢复、安装与代表性原生任务证据，以及限定的协作和经验试用观察。具体结果只支持对应层次。原不完整的基线观察仍保留失败；真实成长试用包含中性结果。

系统不认证普遍成功率、跨工具因果提速、实际账单或人工节省、任意外部写者控制、GUI 模型取消或跨用户受保护恢复。分布式集群、向量记忆和自治发布不属于当前已交付能力。设计、验证与这些取舍的关系见[核心设计](CORE_DESIGN.md)。

## 9. 启用模式

简单任务通常沿用项目规则即可；需要跨轮恢复时保存基本项目记录；长期或多阶段工作采用明确阶段与任务；协作和无人值守需要对应范围。报告、交接、深度检查和复盘按需要启用，不因每轮成功都重写控制记录。

成本考虑包括模型调用、等待、准备、验证和整合。读取当前所需资料、复用有效证据与选择合适分工有助于控制开销，但不能把局部观察直接变成普遍节省承诺。预算以累计消费为准，中断恢复或新执行轮次不补充旧额度。

## 10. 公开发布内容

可复用系统包含 Skill、运行模板/清单、确定性服务、生命周期脚本、原生适配和产品指南；用户项目数据库、会话、凭据及私有证据不属于分发输入。见[发布归档](RELEASE_ARTIFACT.md)和[安全](SECURITY.md)。

## 11. 实现的延续关系

2.0.0 将项目、阶段、任务、操作和证据统一到所选状态库及服务。CLI 与 MCP 使用相同业务合同；Skill 提供工作方法；模板和检查清单用于起草与验证；报告和交接提供阅读视图。这些组件共同支持前述工作过程，不是独立产品。

项目、阶段和任务的技术实体分别称 Project、Phase 和 Task；详细字段留在[状态合同](V2_STATE_CONTRACT.md)。旧文档和历史资产可以通过显式审阅采用到当前运行方式，但不能成为已采用工作区的另一套可写状态。安装更新与项目采用分别执行，恢复保持在当前系统内。

v1 系列建立目标、恢复文件、模板和生命周期治理；当前任务服务进一步持久维护版本、效果和验收，产品用途没有改变。历史发布详情留在 [CHANGELOG](../../CHANGELOG.md)，不组成当前任务队列。

当前运行时保持原有工作目标，将可执行事实交由所选状态库管理。用户计划和交接仍是有价值的叙述输入，任务服务使相关版本和效果关系明确。变化在于状态如何被执行约束，并不要求丢弃项目知识。

迁移是明确所属变化，采用旧工作区前核映射、写者、未知效果和备份。采用后 binding/source-seal 标识边界，旧 Markdown 写入不能成为另一份当前权威。安装与采用的区别见[更新](UPDATE.md)。

## 12. 与详细设计的关系

先按[快速开始](GETTING_STARTED.md)安装并核入口，再根据[使用指南](USAGE.md)选择工作流。当前项目先检查既有进度；新长期目标才初始化。详细控制端协议见[操作参考](V2_PREVIEW_USAGE.md)，升级与恢复见[生命周期](LIFECYCLE.md)。

[核心设计](CORE_DESIGN.md)保留完整模型、运行章节与取舍；[状态合同](V2_STATE_CONTRACT.md)定义当前精确协议。

## 工作区管理数据与迁移

普通新工作区通过 `workspace-init` 默认将任务库、受管证据和恢复资料置于所属 `.malts` 目录，显式外置布局继续受支持。安装更新不搬动已有项目。健康已采用库可经只读计划、备份恢复、当前效果审查和正式前向切换重定位；新 epoch 不恢复旧授权或验收，也不自动激活 Phase。旧库、外部历史引用和来源封存按实际依赖保留。操作与限制见[工作区管理与状态库重定位](MANAGEMENT_AND_RELOCATION.md)。
